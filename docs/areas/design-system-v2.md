## 0. Why this exists: one app, one look

The point of this system is **consistency**. The same kind of information looks and behaves the same on every screen, whichever story built it and whoever uses it (engineer, knowledge admin, account admin). A user who has learnt one table, one status pill or one jurisdiction chip already knows them everywhere else, so the app feels familiar and easy, even on a screen they have never opened.

- **Same data, same component.** A jurisdiction is always the blue globe chip, a status is always its pill, a due date is always the Report due cell, a list of records is always the standard table (section 2). Never restyle one for a single screen.
- **Look before you build.** Before designing or coding a screen, find where the app already shows the same kind of thing and reuse that component and layout. Only if nothing fits, make a new pattern, mark it "NEW pattern" on the canvas, and add it here once approved.
- **Reference screens** (copy these when showing the same kind of thing):
  - Records in a table, with filters, row actions and footer counts: the Observations tab (CP-22) and the Assessments / Clients lists (CP-23).
  - A record's own page (header, chips, tabs, side facts): the client page (CP-23).
  - Adding or editing a record: the Add observation form (CP-22) and the New Assessment form (CP-23).
  - Files and uploads: the client Documents tab and the reading screen (CP-23).
- **A baseline, not a ceiling.** The canvas mock screens and this file set the direction. Build and Check should make the real screens look better than the mocks (spacing, alignment, motion, detail), never different in kind.
- **Check enforces it.** Every new screen is compared with its approved board and with the reference screen for its kind of content before Jesper sees it.

## 1. Principles

1. **One font.** The system font (SF Pro on Apple devices): `-apple-system, BlinkMacSystemFont, "SF Pro Text", Inter, system-ui, sans-serif`. No second family.
2. **Navy is for actions and titles.** Primary buttons and page/card titles use `--marsh-navy`. Nothing decorative is navy.
3. **Colour means something.** Red = late or an error, amber = soon or not sure, green = done or new, and the category colours (jurisdiction, facility, assessment type, file type). Never colour for decoration.
4. **Quiet surfaces.** Thin 1 px borders, no heavy fills. Shadows only on things that float (popovers, menus, toasts, the Create button).

## 2. Rules every screen follows

- **Icons first for actions.** Row and secondary actions are 32–36 px round icon buttons: bin = remove, rotate-ccw = retry, archive, chevron = open, pencil = edit, plus = add, download. Bins are red; every other icon is quiet grey. Words only for the one main action of a screen (Create, New assessment, Upload, Cancel).
- **Tooltips name the action only** ("Rename client", "Delete document"), never the client, site or file, so a long name never buries it. The screen-reader name still names the item ("Rename client NUS"): pass `tooltip` beside `label` on IconButton, RowAction or NavAction.
- **Not allowed yet: grey out and explain.** A blocked action stays visible, greyed and focusable (`aria-disabled`). Hover, focus or tap opens a reason box saying why ("Can't remove yet · This client has 1 open assessment. Archive it, then remove the client."). No error after a click, and no names in the reason.
- **Hover by background.** Hover changes the fill, not the border: grey on white, white with a ring on grey, darker on grey buttons, a white veil in segmented tracks and on navy. The surface sets it; hover only where a pointer can hover.
- **Dropdown options keep their icons.** If a value shows an icon anywhere in the interface (a status pill, a type tile, a Report due state), its dropdown option shows that same icon and colour. Values with no icon of their own, such as jurisdictions, stay plain.
- **Keyboard-only focus ring.** The navy focus ring shows for keyboard use only (`:focus-visible`), never after a mouse click, on every control.
- **A toast for every confirmed action.** Create, save, delete, archive, upload and restore each show a toast (section 7), so the state is always clear.
- **Collapsed sidebar = full width.** When the sidebar collapses, the page content fills the full width, keeping its 32 px side padding. Check every screen with the sidebar open AND collapsed.
- **Layout.** Navy sidebar on the left, in navy, white and one light blue only (the avatar), with no accent colours. The one exception is the Inbox's red count, like the bell's, because it means work is waiting; the collapsed rail and phone menu show it as a dot. A white top bar holds the round Back button (section 6) beside the eyebrow and page title, the main action (top right) and the bell. Page background `--graphite-50`, cards white.
- **One list frame.** Every list screen: top bar with one helper line under the title (what the page is for), then a 64 px toolbar (search, filter pills, a labelled sort pill, the main button at the right end), so every list's header row starts at the same height.
- **No filler copy.** No captions explaining the obvious ("Kept under the client"), no counts in page headers; the one helper line under a list's title is the exception. Counts live in the table footer ("5 assessments · 3 reports late", the late count is a filter link). Help goes behind a (?) icon.
- **Words.** Plain English, short. Use "assessment type" (First survey, Resurvey, Follow-up); never "visit". Errors say what's wrong in ≤ 4 words, then the fix.
- **One flowing sentence.** A line of copy reads as one sentence, never a clipped short one tacked on the end. Not "Add at least 1 observation to Sections 9 and 11. Then you can draft." but "Add at least 1 observation to Sections 9 and 11, then you can start drafting."
- **Tables.** The name column (Client, Assessment, Document) is left-aligned, header and content; every other column is centred. A labelled sort pill names the current order and the sorted column shows an arrow; groups reorder with it. A row that just changed (created, uploaded, edited) holds a soft blue tint for 1 s, then fades. Columns spread across the full width; the hover-actions column is only as wide as its icons (32 px each + 2 px gaps). Fixed-content columns get fixed widths (Report due 168 px, small numbers 64 px). Long text wraps to at most 2 lines, never widens a column.
- **Forms.** One full-width column. Fields 40 px high in rows (e.g. Site name | Jurisdiction | Facility type, then Address full width). "Add …" actions are slim dashed rows. Cancel and Create sit in a sticky action bar at the bottom of the window (section 6); the top bar keeps only the title. On Create with missing fields: scroll to the first one, turn its border red and show one short line under it; pressing Create again gives that field one small shake. No error box or banner.
- **Dates.** Typed and shown as dd/mm/yyyy in forms; tables and pages show "12 Nov 2026".
- **Not-sure values** (AI-filled, needs a look): amber border and tint with one 16 px warning icon, centred in the field, 12 px from its right edge (8 px left of a dropdown's chevron), no caption.
- **No "made by AI" labels.** New screens don't mark things just because the AI made them: no "AI draft", "AI-generated" or "AI proposal" badges and no AI tint or rule on AI-written text. Violet itself is fine for anything it already means (statuses, the site walk proposal, email tiles). Existing screens stay as they are.
- **Phone.** Everything works at 375 px: no sideways scroll, 44 px tap targets, 16 px text in inputs (no zoom on focus), safe areas (`viewport-fit=cover`), tables reflow, dialogs fit, and popovers and menus become sheets under 768 px (`mobile-native` skill). The phone top bar is the sidebar's navy (`--surface-nav`) with the stacked wordmark; the drawer is the desktop sidebar.

## 6. Components (all drawn in the artifact)

- **Buttons:** primary navy pill (New assessment, Create), secondary pill (`--graphite-100` fill: filters, Documents · 3), icon buttons (section 2). A secondary pill that sits on the grey page, where the grey fill would be lost, takes the light ink blue of the Add location row (`Button` `variant="pill-ink"`: `--ink-100`, `--ink-200` on hover, navy text; Site walk proposals, CP-24).
- **Status pills:** Draft (violet), Not started (grey dashed circle), Under review (amber), Archived (outline). Icon + word. A long label (the stage "Ready for generation") draws on two lines that hug its words (`StatusPill` `lines`, `data-lines="2"`), never one wide pill. On a white menu the icon takes the pill's `ink` colour, so a pale one (Exported's green tick) stays visible.
- **Chips:** jurisdiction (blue, globe icon), facility (teal, building icon). Plain, no border. A client's division is plain text (facts panel, Clients table's second line), not a chip.
- **New badge:** green tint, green text, 12 / 700.
- **Tag pill:** fixed width so every row matches: 164 px in tables, wider in the documents popover (sized in Build so a long "Site · Assessment" fits). Tag icon first, chevron last; long text ends in … with the full name on hover.
- **Date cell** (`ReportDue`): calendar icon 8 px from the date, centred on its two lines; date 14 / 500; a 12 px second line, at most two lines. Report due: late = calendar-x and red "N days late"; within 7 days = calendar-clock and amber "in N days"; on track = grey "in N days"; none = grey "Not set". Next survey uses the same cell with its site as the second line (`note`), never late; in the Clients list it drops the icon (`icon={false}`) so a long site name can't push it away. No coloured fills.
- **Segmented control:** First survey / Resurvey / Follow-up, each with its icon and wearing its assessment-type colour; the white thumb slides to the choice and the tile beside "Assessment N" follows it. Sits on the "Assessment N" header line.
- **Shaded icon action** (`IconAction` `shaded`): a round icon button on a `--graphite-100` disc, `--graphite-200` on hover and press. For an add action once its list has items (Add Document in the Details panel), beside plain icon siblings such as Edit Site. Like controls in one panel share one style: no labelled pill beside icon buttons.
- **Back button:** a round 36 px button beside the page title: `#eef1f6` at rest, `#e3e8ef` on hover, scale 0.96 pressed, navy focus ring.
- **Reason box:** a small white box (popover look) tied to one control: a short title and one line saying why. Opens 150 ms after the pointer rests, on focus, or on tap. Use it instead of a plain tooltip whenever the answer is "why not".
- **Date picker** (`DatePicker`): a dd/mm/yyyy field; a click or tap anywhere on it opens the calendar (popover on desktop, centred card on a phone) while focus stays in the field, so typing still works. Typing adds the slashes (8 digits fill it; "1/" pads to "01/") with the rest of the mask shown faintly; number pad on phones. Calendar: month arrows, Today, Clear; a click on the month or the year in the heading swaps the days for twelve months (the arrows step the year) or twelve years (this year fifth, the arrows page twelve at a time); those before a minimum are greyed, picking one keeps the day (or the month's last), and Esc goes back to the days; days before a minimum greyed, today ringed, 44 px cells on phones, full keyboard.
- **Sheet:** a bottom sheet on phones (44 px rows, Cancel at the bottom, no close icon), or a centred card for the date picker.
- **Sticky form action bar:** Cancel and Create pinned to the window's bottom edge, 48 px, 16 px text; Create swaps its word for a spinner in the same width while saving.
- **Dialog** (the chat's Apple sheet in the app font; `Dialog` adds `ds-dialog--v2` to every dialog, so no caller passes it): 18 px corners, no border, shadow `0 24px 64px rgb(0 15 71 / .18), 0 2px 8px rgb(0 15 71 / .08)`; title 19 / 600 navy; a round grey close button floating in the corner, so the helper text runs the full width (14 px, normal line filling, no balanced wrapping); no footer band; pill buttons, 44 px and equal width on phones. Helper text says the consequence and the way back in one or two plain sentences, never repeating the title ("It won't be offered for new assessments. Existing assessments stay as they are, and you can restore it from Removed sites."). Titles name the thing ("Rename Northgate Freight Group"); buttons name the action. Every dialog with a close button (an `onClose`) also closes on a click outside its card, but only when the press began outside too, so a text selection dragged out of it stays open; a dialog with no `onClose` never does. Its header (title and close button) stays at the top while a long dialog scrolls, on the card's colour, with a hairline under it once the content has moved.
- **Pagination** (`Pagination`, IN-17): under a paged table, opposite the footer count ("Passages 26–50 of 1,214"): a 32 px outline chevron button, "Page 2 of 49" (13 px grey, the numbers 600 with tabular figures), another chevron. 44 px buttons on touch screens; a button is greyed out at either end, and the pager is hidden when one page holds everything. Use it when a list is too long to load at once; a list that grows as you read uses a Load more row instead.
- **Search field with a switch** (`SearchField` `end`, IN-17, NEW pattern): a segmented control inside the search field's right end, 4 px in, its track `--graphite-200` on the field's `--graphite-100` so the two read as one piece; options 28 px tall (44 px on touch, the field growing to 52 px). For a choice of how to search, never a filter. A choice that costs a paid call (Meaning) runs on Enter, says so in the placeholder ("Describe what you're looking for, then press Enter") and in a 12 px grey "Press Enter to search" under the field while typed words wait; the footer names what was searched ("Passages 1–20 of 20 matching “…”"). A disabled field greys out whole.
- **Paged table with an opening row** (IN-17 Passages, NEW pattern): one card of a native table whose name cell is the row's disclosure button (chevron, then at most two lines); opening a row shows a full-width detail row on the sunken surface with the 2 px ink rule, one row open at a time. Filters sit above the card and go back to page 1; while the next page loads the old rows stay at 55 % opacity; the first load shows five pulsing grey rows. Below 768 px each row is a card: place and heading, the excerpt, then type and pages.
- **Long lists in popovers:** five rows show, the rest scroll with a fade and a scroll bar; the add row stays in view. Popovers float above every card and the sticky bar.
- **Dashed add row:** full-width, 40–44 px, 1.5 px dashed `--graphite-300`, navy text with a plus.
- **File tiles:** email violet, PDF red, Word blue, text grey; unknown types grey.
- **Fields:** normal, not sure (amber, section 2), error (red border + one line under it).
- **Found so far** (reading screen): Client, Sites, Assessments groups, each only as tall as what was found once the read is in; grey placeholder rows while reading.
- **Documents popover:** opened from a "Documents · N" button in the client card; rows of file tile, name + size, Tag pill, bin; a dashed "Add documents" row. No caption.
- **Reading status cell** (files being processed): words first, then the indicator at the right edge. Working = status words in 13 px `--graphite-700` + a 16 px spinner; Waiting = "Waiting" in `--graphite-600` (the words need 4.5:1 contrast) + a 16 px hollow circle in `--graphite-400`; Done = 16 px green filled tick only. **Spinner, circle and tick are the same size and sit in the same pixel column.**
- **Insights tab** (CP-29, NEW pattern): a record's analysis sits on its own tab, last, so the tab the page opens on is unchanged. One grey line states what the figures are counted from. Then, top to bottom: figure tiles (label 12 / 600, value 28 / 700 navy, a 12 px note that is red or amber with a warning icon only when it needs attention; two to a row on a phone); "What stands out" cards (a 32 px icon tile in the finding's tone, a 15 / 600 sentence, one grey line, a share as an 8 px meter on `--ink-100` filled `--ink-600` or a change as "5 → 7", and a text link to the block that shows it); the Summary card; and the ranked list. A chosen site dims the others to 38% in every block below. Built from an approved clickable mock; to add to the canvas.
- **Ranked list with reasons** (CP-29, NEW pattern): rows of rank number, 32 px site tile, name, a grey line and reason chips (red for Critical findings, Priority 1 OFIs and a late report; amber for High findings, uncategorised and a poor rating; green for improved; grey otherwise). One grey line above the list states the order. The row is a toggle (`aria-pressed`); a chevron at its end opens the record. Never a score.
- **Shaded grid** (CP-29, NEW pattern): a table whose cells are 44 px buttons shaded by count on the ink ramp, `--ink-50` to `--ink-600`, relative to the largest cell, with the count printed in every cell (dark text to `--ink-400`, white from `--ink-500`) and 2 px of card between cells, no borders. A cell with none is `--graphite-50`. A chosen cell, or a column a finding points at, takes a navy ring with a white one inside. A "Fewer … More" key sits under it, and a readout line on `--graphite-50` says what the cell under the pointer or focus holds. It scrolls sideways in its box under 520 px. Never `--chart-*`, severity or AI colours.
- **First-to-latest row** (CP-29, NEW pattern): a table row of name and period, a hairline axis with a light dot (first, `--ink-400`), a dark dot (latest, `--ink-700`), small grey dots for visits between and an `--ink-200` bar joining first and latest, then the figures ("5 → 7") and a chip (Improved with a tick, Worse with a warning, or a grey First visit, No change or Not entered). A segmented control above it picks the measure; a two-dot legend names the dots; three ticks sit under the axis. Dots move 180 ms when the measure changes, not at all with reduced motion.
- **Written summary** (CP-29, NEW pattern): as the Ask tab's answer, without its left rule: `ConfidenceIndicator` and a round Write again button on the heading line; a 12 px grey line saying the model drafted it, when, from what, and that it is not in any report; statements at 14 / 1.65 with violet citation numbers that mark their source; an "Evidence missing:" line on `--graphite-50`; and Sources, six shown then "Show all N sources", each with its number, title, a grey line and the source's own words. Unwritten: one sentence and a primary Write summary. Writing: a violet pulsing dot and grey bars. Out of date: an amber callout with Write again. Stopped: a red callout titled "Summary stopped at 14:02" with the reason. Violet here is the same exception as the Ask tab's.
- **Calendar grid** (CP-60, NEW pattern): a card whose toolbar holds the period stepper (chevrons each side of "November 2026", 16 / 700 navy, 200 px so the arrows don't move; in the month view the month and the year are buttons that open the date picker's month and year choosers in a popover), Today, a Month / Week segmented control and the filter pills, with New assessment beside the bell. Under it, a row of weekday names (12 / 600) and one row per week, 148 px tall in the month and at least 440 px in the week, hairlines in `--graphite-100` between days and weeks. A day shows its date top left (13 / 500; the first of a month reads "1 Dec"); days outside the month are on `--graphite-25` with grey dates; today's date is ringed in navy, as in the date picker. A round + appears top right of a day on hover or focus (always, where there is no pointer to hover with). A month day shows three entries, then a grey "+N more" that opens its week. The arrow keys move between days from one tab stop.
- **Calendar entry** (CP-60, NEW pattern): 24 px tall in the month, 60 px with a second line in the week, radius 8, 12 / 600, 4 px from the day's edges. A survey is a bar in its assessment type's tint and colour with the type's icon, one bar across all its days, square at an end that runs into another week. A report due date is a white chip with a 1 px `--graphite-200` border and no fill; its icon and words take the Report due cell's state (red calendar-x, amber calendar-clock, grey calendar, a green tick once finalised). ## 7. Toasts

Use **Sonner** (`ask-sonner` skill), styled to this system and wrapped in our own `Toast` helper so callers don't depend on Sonner directly.

- Sonner's default behaviour: stacked (newest in front, older ones peek behind and spread on hover), swipe to dismiss, pauses on hover and while the tab is hidden, a loading toast that turns into success or error (`toast.promise`).
- Our styling: white card, radius 14, 1 px `--graphite-200`, the popover shadow, 14 px text with the title in `--graphite-900`; icon only coloured: green tick for success (our own `SuccessIcon`, the tick raised 0.4 units to its optical centre), red alert for errors; an icon-button close. The icon is centred in the toast's height, on every toast. The toast hugs its message, centred, up to 356 px; longer text wraps.
- Every toast goes through the one `toast.*` helper (success, info, error); the older `Toast` component is gone, so there is one icon and one layout.

- Every confirmed action gets one (section 2).

## 8. Motion

Built with the `animate` skill, reviewed with `review-animations`. Motion only to give feedback, show where something came from, or bridge a change; under 300 ms for UI; never on things used many times a day. Animate `transform` and `opacity`; with reduced motion, fade only. Use the existing tokens in `motion.css` (`--ease-out`, `--ease-standard`, `--duration-fast` 120, `--duration-base` 180, `--duration-slow` 260) and add `--duration-scroll: 450ms` and `--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1)`.

## 11. Appendix: carried over from the old design-system.md

The old `docs/design-system.md` was merged into this file on 2026-11-20 and deleted. Where this appendix disagrees with sections 0 to 10, those sections win on look and feel. It keeps what v2 does not say: wording rules, chart rules, the component inventory, runtime behaviour and per-screen notes.

### Content fundamentals (wording)

**Voice: a careful colleague, writing for the record.** Short declaratives. No marketing register, no encouragement, no personality.

- **Person.** Address the engineer as _you_ ("Your sign-off is recorded"). The system is _it_, never _I_ — it does not say "I found 4 sources", it says "Drafted from 4 sources". Never attribute judgement to the AI; it drafts, cites and flags. It does not "think", "believe" or "recommend" — recommendations belong to the engineer.
- **Casing.** Sentence case everywhere: buttons, headings, table headers, menu items. The only uppercase is the 11px structural label (`EVIDENCE`, `SECTIONS`, `STATUS`), letterspaced 0.08em.
- **Buttons are verbs.** "Generate draft", "Accept", "Resolve", "Finalise and issue". Never "OK", "Submit", or "Click here".
- **Numbers are exact and unrounded.** "24 evidence items", "6 of 6 sections reviewed", "£1.4m estimated BI exposure". Confidence is never a percentage — the platform does not claim that precision, so it is High / Medium / Low with a three-bar meter.
- **Errors state cause, then next step.** "Standards library sync failed at 09:12. Retry, or continue with the cached copy from 08 Apr." Never "Oops" or "Something went wrong".
- **Empty states state the cause, then the trigger.** "No reports assigned — reports appear here once a survey is scheduled to you."
- **Dates and clauses are literal.** `11 Apr 09:22`, `FM Global 2-0 §2.4.1`, `RPT-2026-0411` — always in mono. Where the year matters, as in an observation's capture time and who last edited, corrected or deleted it, which are evidence, the date carries it: `11 Apr 2026 09:22`.
- **Quotations are verbatim.** Evidence excerpts are quoted exactly, never paraphrased, and sit behind a 2px left rule.
- **No emoji. Ever.** Not in UI, not in notifications, not in exported reports.

Sample microcopy, in register:

> First draft generated 11 Apr, 14:02. Drafted from 12 site observations, 4 past reports and 8 external standards. Every passage below is attributed — review before sign-off.

> 3 findings unresolved. Sections with open uncertainties cannot be finalised.

### Charts

**Charts.** Four chart types: the vertical stacked bar of the usage and cost screen (`client/src/features/usage/components/StackedCostChart.tsx`, Recharts), and the report's donut, bar (vertical, or horizontal for long labels) and grouped bar under Sections 3 and 4 in Review (GN-12, `client/src/features/assessments/components/ReportChart.tsx`). The report's charts follow Marsh's titles and value order and keep every value in the legend and table even at 0. Unlike every other chart, they take Marsh's own palette, the `--report-*` tokens sampled from the sample reports (Miya, 20 Oct): navy bars and current scores, sky potential and client scores, teal for the occupancy peer group, the Risk Assessment Matrix's orange-to-green for priorities, and Marsh's colour per OFI status. The Risk Assessment Matrix and the Rating Legend use the same tokens. Each value keeps its colour between reports. Series take the `--chart-*` tokens and nothing else. Each billed vendor has one hue family, with a dark and a light step where it bills two services: Anthropic blue, Google aqua, OpenAI magenta, Cohere orange, Typesafe olive, and grey for the free self-hosted OCR. Red, amber, green and violet are never used for a series, because they mean severity, review state and AI provenance. A feature takes the hue of the vendor that bills it most; Google's two report features take its two steps (photo reading light, handwriting transcription dark). Aqua dark was re-stepped from `#0d8a6a` to `#008d65` for handwriting (CP-19): beside voice transcription's magenta dark the old step fell to CVD ΔE 5.8 (deutan), below the floor; the new one clears 6.5 there and 9.7 on the ingestion charts, and no other aqua or teal step passed against both magenta dark and Anthropic blue. Knowledge base search (IN-17) is the one feature outside the vendor rule: Cohere bills it, but both orange steps belong to features that share an engineer's bar with it (retrieval, chat) and no third orange clears the normal-vision floor (best 14.5), so it takes `--chart-sky` (`#44bcfc`), the step furthest from all eight report hues (worst ΔE 15.8 normal, 12.9 protan/deutan, 27.5 from the AI violet). Parts stack in one fixed vendor order, never by cost, so a part keeps its place and colour when another comes or goes. The set was validated with the dataviz palette validator on the white card surface (OKLab ΔE ×100): every pair that can share a bar clears the normal-vision floor of 15 and CVD ΔE of 6 or more. The light steps sit below 3:1, so every chart also gives its values as a table, and the screen lists every group in a table below it. The marks: bars at most 24px wide, a 2px card-coloured gap between parts, 4px rounded data end, hairline grid and no dashes. Legend and tooltip text stay in text colours; only the swatch or the short line key wears the series hue. The legend appears for two or more parts. The tooltip leads with the value.

### Per-screen design notes

These notes preserve the original design intent. References to recording, attachments, sign-off and export describe the intended product; the current UI simulates those services.

#### Assessments dashboard

The engineer's home. Every assessment assigned to them, with the work outstanding on each.

- **1. Two entry points, one primary.** New assessment is the only primary button on the screen. Continue capture sits beside it as a secondary action, so an engineer back on site reaches capture in one tap. It names the site it opens: the engineer's own assessment with capture in progress, or the most recently started if there are several. With no capture in progress it is hidden, and capture starts from the assessment's workspace.
- **2. Filters narrow, they do not hide.** Search matches site, client and report ID as you type. The result count next to the filters always states what is being shown, so a filtered list is never mistaken for an empty queue.
- **22. Outstanding items are the sort signal.** The last column counts unresolved uncertainties rather than progress. It is the number that decides which assessment an engineer opens next. Click any row to open RPT-2026-0411.

#### Create assessment

Three decisions: where, what kind, and who signs it.

- **3. Site before everything.** Site and client are the only required fields. Everything else can be completed after the visit, so an engineer standing in a car park can open an assessment in seconds.
- **4. Drafting chooses the standards, not the form.** There is no standards picker. Drafting searches the whole knowledge base for the site's jurisdiction and facility type, and every citation names the document it came from, so a reviewer can still trace each one.
- **5. The first engineer is the lead.** The lead engineer badge follows the first person selected. Sign-off is recorded against that name at export.
- **6. Validation states cause, then next step.** Submitting with an empty site or client shows one callout naming both fields and colours their borders, rather than a modal. Correct them and create again.

#### Site observation

Captured on site or at the desk. Everything here becomes citable evidence.

- **8. One observation, four input modes.** Note, voice, photo and scan are modes of the same record, not four separate records. Whichever mode you use, the observation detail below is the same, so nothing reaches the report uncategorised. Each mode shows on the switcher what it holds, so nothing waits unseen behind another.
- **23. Voice is transcribed, never interpreted.** Stopping a recording produces a verbatim transcript in violet AI chrome. Edit as text note converts it into your own words and the violet chrome disappears — the words are then yours.
- **30. Handwriting is transcribed, never interpreted, and its doubts are shown.** A scanned page of notes is written out word for word, the engineer's abbreviations and spelling kept, behind the violet AI rule beside its original, which opens to zoom into. A word the model could not read for certain is its best guess, underlined (dotted, AI violet, so it reads without colour too, and "unsure" to a screen reader), with how many there are above the text: "2 words unsure. Check them against the page." A guess is never dropped silently and never shown as certain.
- **27. Photos are interpreted only when asked, and only as a proposal.** Saving never sends a photo to the model; Read photos does. A photo's reading is the model's, not the engineer's: it stays in violet AI chrome beside the photos it came from, and reaches the report only when the engineer saves it into the note or the category through Edit.
- **24. Metadata is mandatory, not optional.** Location, risk category and severity are what let a generated passage cite this observation. Severity uses the same four-step scale as the report, so field grading and report grading never diverge. Nothing is pre-selected or carried over from the last observation: a severity nobody chose would reach the report as a finding.
- **28. Capture is part of the Observations tab.** Add observation opens it within the assessment, under the same header and tabs, and ← Observations goes back: the label names where it goes rather than declaring the work done. Capture keeps no list of its own; the Observations tab is the one list.
- **25. Targets sized for gloves.** Every control on the phone is at least 44px tall, and Save observation is a full-width large button pinned above the home indicator.

#### Report generation

Section-by-section drafting, with every failure visible while it happens.

- **7. Tabs are the assessment, not the app.** Generation, review and export are stages of one report, so they are tabs inside the assessment rather than separate destinations in the sidebar.
- **9. Stopping is always available.** Stop generation asks for confirmation and names what will be kept. Sections already drafted are never discarded — drafting resumes from the first section that did not complete.
- **10. Insufficient evidence is not an error.** The section states what is missing and offers the two real routes out: capture the evidence on the phone, or write the section yourself. It never drafts an unsupported passage to fill the gap.
- **11. Failures name cause and time.** A failed section reports the cause and the timestamp, then offers retry or the cached standards copy. The engineer chooses whether stale standards are acceptable.

#### Report review workspace

Sections left, draft centre, provenance right. The engineer signs what is in the middle.

- **12. The rail is the review ledger.** Each section carries its own review glyph — AI draft, edited by you, accepted, needs review — and the bar above counts how many are done. Selecting a section changes the centre and the right pane together.
- **13. Reject removes in one click.** Rejecting drops the section out of the report immediately; the rail marks it Removed and the centre offers Restore this section. Accept and Edit sit in the passage footer, where the words are.
- **14. Unsupported claims are marked, not deleted.** A passage with no source behind it keeps an amber underline and an inline flag until it is resolved. It cannot be accepted away — the resolution happens in the right pane.
- **15. Conflicting sources ask, they do not choose.** Where two sources disagree the draft shows the conflict and names both figures in the evidence list. The engineer picks which one stands, and the sentence rewrites.
- **16. Open items sit with the evidence.** Resolution options are in the right pane, beside the sources they concern, rather than in a separate task list. Resolving one updates the draft, the rail and the export checklist at once.
- **17. Citations are two-way.** Superscript markers in the draft are clickable; the matching source highlights in the evidence list. Every generated sentence has a route to what it came from.
- **18. Original observations stay verbatim.** Beneath the sources sit the engineer's own field records — photograph, voice note, written note — quoted exactly as captured, never paraphrased by the system.
- **29. The document is the whole report.** Edit document opens every section as one page, in report order, so a missing or weak section is written where it sits rather than worked around. The structure is the template's and stays fixed; only the text moves. Violet marks what the draft still says word for word, so the engineer can see at a glance what they have not yet made theirs.
- **31. Nothing written is lost.** Every draft and every save of a section is a version, compared with the current text word by word before anything is restored, and a restore is itself a new version, so it can be undone the same way. A restore changes one section only.

#### Validation and export

The checks that stand between a draft and an issued report.

- **19. Blocked export explains itself.** The callout names the number of failing checks and the export button is disabled rather than hidden, so the engineer can see what the button will do once the checks pass.
- **20. Every outstanding item is one click from its section.** Go to section switches to the review tab and selects that section, with its open item already showing in the right pane.
- **21. Format and content are separate decisions.** DOCX for client review cycles, PDF for issue. Citations and the photograph appendix are independent of format, so a client-facing DOCX can carry the full evidence trail.
- **26. Resolve everything to unblock.** Accept or edit all seven sections and resolve the three review items, and the callout turns to Ready to export with the button enabled.
