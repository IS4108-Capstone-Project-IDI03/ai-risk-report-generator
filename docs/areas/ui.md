# UI conventions

<!-- at-a-glance -->
> **In 30 seconds:** rules for building any screen: reuse the design-system components and tokens, and follow `docs/areas/design-system-v2.md`.
>
> **Read this when:** you start a new screen.
<!-- /at-a-glance -->

Read [the Marsh design system](./design-system-v2.md) before changing any screen. It is the visual and component reference for every future screen.

- Put reusable, domain-independent controls in `client/src/design-system/components` and export them from `design-system/index.ts`. Use typed props and ordinary React imports.
- Put screens, workflow-specific panels and state in their feature folder. Keep tests and feature styles alongside the feature. Keep `App.tsx` focused on the entry flow.
- Reuse the shared Button, Input, Select, Card, Tabs, SideNav, feedback and AI components before creating another control. Use semantic CSS variables for colour, type, spacing, radii, elevation and motion. Add a shared token only when the existing scale cannot express the design.
- Keep all token imports in the shared stylesheet, loaded once by `index.css`. Do not load standalone prototype HTML, runtime scripts or global component bundles.
- Use the system font stack (`--font-sans`: San Francisco on Apple devices) for UI, IBM Plex Serif for report prose and Mono for identifiers/figures. The one exception is the document editor's Page layout (RV-12), which sets the report in Arial, as Marsh's own reports are (`document/page/pages.css`). The export (EX-01) prints those same pages, so whatever Page layout draws is what the PDF holds: style a report part for the page in `pages.css`, and keep screen-only controls out of the page view. The sidebar shows the Marsh logo image (CP-23); elsewhere Marsh is a text wordmark. AI violet identifies provisional machine-written content; severity and lifecycle colours retain their meanings.
- Draw charts with Recharts, coloured only with the `--chart-*` tokens (see "Charts" in the design system), never with severity, lifecycle or AI colours. Give every chart a legend for two or more series and its values as a table, since the light chart colours are below 3:1. A new series or palette change is re-run through the dataviz validator first. A chart that knows its domain (the usage chart knows billed services) lives in its feature folder, not the design system.
- Show a cited knowledge-base passage with `client/src/features/sources/`: `PassageBody` for its text (quote marked, formulas as math) and `CitedRegion` for the part of the original page it was read from (KB-02). A new screen that cites passages reuses them rather than printing the text in its own block.
- A screen open to more than one role hides the actions a role lacks, rather than showing them disabled. Check with `can()` from `features/auth/access.ts`. For example, engineers browse the Knowledge base read-only (IN-17): Documents only, no Review page, and no action that changes a document. Hiding is for the user; the gateway's permission check is the boundary.
- Use sentence case, concise explanatory errors and verb-labelled actions. Every generated passage must expose evidence and a review state. Confidence is high/medium/low, never a percentage.
- Use the shared size variants for controls in the same row. Preserve the documented prototype exceptions when editing migrated screens; use the shared scale for new screens.
- Keep the 1080px stacked-layout and 760px mobile-navigation breakpoints. Check actual overflow and scrolling, not only conditional rendering.
- Use native form controls, accessible names, visible focus, keyboard-operable interactions and shared native dialogs. Respect reduced motion. Do not add UI controls with silent no-op actions; explain unavailable demo functionality.
- Demo state is memory-only. Never persist passwords or imply that simulation authenticated a user, uploaded evidence, generated a real report or issued it.

Run `npm --prefix client run build`, `npm --prefix client run lint`, and `npm --prefix client test` after functional changes. Visually review affected screens at desktop, tablet and phone widths. Browser availability is required for visual review; jsdom cannot verify layout or native focus trapping.
- The Observations tab is a location navigator beside a compact one-line list; each observation opens on its own page, edited in place. Capture is Record site walk (client/src/features/site-walk/) or Add manually. See docs/areas/design-system-v2.md.
- The tab's List / Buildings switch (CP-61) swaps the navigator and list for the building stack (`components/BuildingStack.tsx`, shapes in `buildingStack.ts`): a cell per location, coloured by its worst observation. It is client only, reading the same locations and filtered observations as the list (`obsStack` in `useAssessmentWorkflow.tsx`), and unlike the list it keeps every location drawn while a filter is on. The view is kept in the workflow's state (`obsView`), so it survives a visit to capture.
- Background work (F-11) is an activity icon beside the bell (`client/src/features/background-work/`), shown only while the user has work queued, running, failed or waiting on them. It carries no count badge (red counts are the Inbox's and the bell's); its name says how many. It opens a popover in the bell's style: "Waiting on you" first, then "In progress" (failed, running, queued). A row shows only what can be measured: an ingestion's stages, recordings or parts as one segment each (`SegmentBar`: done green, under way sweeping, failed solid red, still to come grey; stages labelled "Stage 2 of 3 · Chunking" with the pages done as words under them, so a row has one bar), other pages or OCR regions as a bar with the real count, and one AI call as a working mark with its minutes, never an estimated percentage. A failure's reason is one line, with the whole of it as its tooltip, so several failures don't flood the popover. The whole row opens its job by pointer, its reason included (Try again excepted), through the openers the screens already listen to (`openWork.ts`; an observation or the drafting tab through `openAssessmentAt`). Placed by `AssessmentApp.tsx` beside each bell.
